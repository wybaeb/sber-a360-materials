# Шаг 1 · Раздатка к трём кейсам встречи

Три кейс-карточки для работы на встрече (по одной на контекст). Собраны на основе
материала Data Category Map из первого захода программы. На каждый кейс — 25–30 минут:
5 минут разбор образца, остальное — участники заполняют по своему подразделению.

Общий маршрут карты, одинаковый для всех трёх кейсов:

> **вопрос → метрика → категории данных → источники → проверка качества → master-source → action plan**

Карта заканчивается не таблицей, а планом действий: что починить, у кого запросить доступ,
какие цифры сверить.

---

## Кейс 1 · Контекст «Продукт» (уровень: один продукт)

**Управленческий вопрос:** почему продукт не растёт так, как заложено в плане?

**Что делаем:**
1. Выписываем 5–7 показателей, по которым вы реально принимаете решения по продукту.
2. Делим их на **опережающие** (конверсия в заявку, время обработки, доля активных клиентов,
   ошибки в процессе) и **запаздывающие** (выручка, доход, отток, P&L-эффект).
3. Для каждого показателя — источник (система / отчёт / человек), владелец, частота обновления.
4. Отмечаем, на каких показателях решение принимается **раньше результата** — это и есть
   ваша управленческая панель.

**Типовые находки:** решения принимаются по запаздывающим метрикам, когда менять что-либо уже поздно;
у половины опережающих метрик нет владельца данных.

**Промпт-помощник:** этап 1 учебного OnePager («Карта источников данных»).

---

## Кейс 2 · Контекст «Процесс» (пример: кредитный конвейер)

**Управленческий вопрос:** где процесс теряет время и на каком шаге данные рвутся?

**Что делаем:**
1. Раскладываем процесс по шагам и напротив каждого шага пишем, в какой системе остаётся след.
2. Ищем четыре типовых узких места ландшафта данных:
   - **дубли** — одна заявка учтена дважды из-за сбоя интеграции;
   - **разрозненность** — шаги живут в разных системах, сквозного идентификатора нет;
   - **пробелы** — шаг не логируется вовсе, срок известен только со слов исполнителя;
   - **частота** — данные обновляются реже, чем принимается решение.
3. Помечаем, какие из узких мест мешают считать сквозное время процесса.

**Типовые находки:** сквозное время процесса нельзя посчитать, потому что нет общего ключа;
самый долгий шаг оказывается тем, по которому вообще нет данных.

## Кейс 3 · Контекст «Бизнес» (уровни: один продукт vs портфель)

**Управленческий вопрос:** почему на совещании у одного и того же показателя две разные цифры?

**Что делаем:**
1. Берём 1–2 показателя подразделения, по которым регулярно возникает спор.
2. Выписываем все источники, из которых эта цифра приходит, и в чём между ними расхождение
   (период, признание, справочник, фильтры).
3. Выбираем **master-source** — единый источник правды — и фиксируем, почему именно он.
4. Сравниваем, как меняется набор данных при переходе с уровня одного продукта на уровень портфеля:
   какие показатели агрегируются, а какие теряют смысл.

**Типовые находки:** master-source выбирается не по качеству данных, а по тому, кто первым
прислал отчёт; на уровне портфеля половина продуктовых метрик несопоставима между собой.

## Что уносит участник

Заполненный черновик карты по одному из контекстов — вход в домашнее задание
(`template_data_source_map.md`), где карта достраивается до 5–10 показателей по всем трём контекстам.
